# 계산 방법론

## 피킹률

### 정의

```
피킹률(%) = (월 추정 최대 혜택 합) ÷ (전월 이용실적 기준 금액) × 100
```

구현은 [`site/picking.js`](../site/picking.js) 의 `computePickingRate` 한 곳뿐이다.
데이터에 저장하지 않고 화면에서 계산한다.

- **분자**: 다음 순서로 정한다.
  1. `integrated_monthly_cap_krw` (카드 전체 통합 월 한도)가 확인되면 **그 값**.
  2. 없으면 각 혜택의 `monthly_cap_krw` 합.
     원화 한도가 없고 `monthly_cap_points` 만 있는 혜택은 **1포인트 = 1원** 가정으로 더한다.
     한도를 모르는 혜택은 **0 으로 계산한다.**
- **분모**: `prev_month_spend_tiers_krw` 중 **가장 낮은** 구간.

통합 한도가 있을 때 개별 한도를 합하지 않는 이유는, 카드사가 카테고리별 한도와 별도로
전체 상한을 두는 경우 개별 합이 실제 상한을 넘기 때문이다. 계산 결과의 `basis` 필드가
어느 근거를 썼는지 알려준다 (`integrated_cap` / `summed_benefit_caps` / `summed_caps_with_points`).

### 포인트 한도 환산 가정

현대카드처럼 한도를 `월 1만 M포인트` 로만 표기하는 카드가 있다. 이 값은 원화가 아니므로
`monthly_cap_points` 에 따로 저장하고, **데이터에는 환산값을 넣지 않는다.**

피킹률 계산에서만 `POINT_TO_KRW_ASSUMPTION = 1` (1포인트 = 1원)을 적용한다.
국내 카드 포인트는 통상 1포인트를 1원처럼 쓰지만 실제 가치는 사용처와 교환 방식에 따라 다르다.
이 가정이 쓰인 경우 결과의 `usesPointAssumption` 이 참이 되고, UI 가 해당 문구를 함께 보여준다.

### 읽지 않는 한도 표기

`주유서비스 월 이용금액 한도 15만원` 처럼 **할인 대상 이용금액**의 상한을 말하는 표기가 있다.
이는 할인 금액 상한이 아니다. 요율 10% 라면 실제 할인 한도는 1만 5천원이므로,
이용금액 한도를 할인 한도로 읽으면 최대 20배까지 과대추정된다.

요율을 곱해 유도할 수도 있지만 서비스 구분명(`주유서비스`)과 혜택명(`주유 할인`)을
느슨하게 짝지어야 해서 잘못 연결될 위험이 있다. 그래서 지금은 **읽지 않는다.**
검증기와 파서에 이 열을 배제하는 규칙과 회귀 테스트를 두었다.

### 이 숫자가 아닌 것

피킹률은 실제 절감액이 아니다. 두 방향으로 동시에 틀린다.

**과대 방향** — 모든 혜택의 월 한도를 전부 채운다는 가정이다.
실제로는 카테고리별 최소 결제 조건, 제외 가맹점, 통합 한도, 정기결제 등록 여부 때문에
동시에 모두 채우기 어렵다.

**과소 방향** — 한도가 확인되지 않은 혜택을 0 원으로 본다.
현재 데이터에서 월 한도를 읽어낼 수 있는 카드는 일부이며, 나머지는 피킹률을 아예
산출하지 않는다. 또 포인트 단위 한도(`4,000포인트`, `1만점`)는 원화 금액이 아니어서
수집하지 않으므로, 포인트형 카드는 한도가 비어 있다.

그래서 UI 는 혜택 몇 건이 한도 미확인인지 함께 보여준다(`pickingCaveat`).

### 계산하지 않는 경우

| 상태 | 조건 | 표시 |
| --- | --- | --- |
| `ok` | 실적 구간 있고 한도 1건 이상 확인 | `피킹률 약 N%` |
| `no_spend_condition` | 실적 조건이 없다고 확인됨 (분모 없음) | `실적 조건 없음` |
| `insufficient_data` | 실적 구간 미확인, 또는 한도를 하나도 모름 | `피킹률 산출 불가` |

실적 조건이 없는 카드에 0 을 넣어 무한대를 만들거나, 임의의 기준액을 가정해
순위를 매기지 않는다. 2026년 들어 전월실적 조건을 없앤 상품이 늘고 있어
"조건 없음"은 결측이 아니라 하나의 상태로 다룬다.

### 보수적 처리

- 범위로 표기된 요율(`3%~10%`)은 상한을 취하되, 이는 표시용이고 피킹률 분자에는 쓰지 않는다.
  분자는 금액 한도만 쓴다. 요율에 가정 결제액을 곱해 혜택을 추정하지 않는다.
- 원본에서 손상된 금액(`16,0`)은 버린다. 추정 복원하지 않는다.
- 세금·공과금·무이자할부는 통상 실적 제외·적립 제외 대상이지만, 카드별로 확인되지 않으면
  `tax` 필드를 비워 둔다.

## 필터 정의

| 필터 | 동작 |
| --- | --- |
| 검색 | 카드명, 소개 문구, 혜택 제목·설명을 부분 문자열로 대조 (대소문자 무시) |
| 카드사 | `issuer` 완전 일치 |
| 카드 종류 | `card_type` 완전 일치 |
| 연회비 상한 | `annual_fee_krw` ≤ 선택값. **연회비 미확인 카드는 제외된다** |
| 전월실적 상한 | 최저 실적 구간 ≤ 선택값. 실적 조건 없음으로 확인된 카드는 항상 포함. 미확인 카드는 제외 |
| 혜택 분야 | 선택한 분야를 **하나라도** 가진 카드 (OR) |

상한 필터가 미확인 카드를 제외하는 것은 의도된 동작이다. 알 수 없는 값을 0 으로 보고
"연회비 없음" 결과에 섞어 넣으면 사용자를 오도한다.

## 데이터 신뢰도

`confidence` 는 카드별로 다음 5개 신호 중 몇 개가 온전히 읽혔는지로 정한다.

1. 연회비
2. 혜택 항목 1건 이상
3. 전월실적 구간 또는 "조건 없음" 확인
4. 요율 1건 이상
5. 월 한도 1건 이상

5개 → `high`, 3~4개 → `medium`, 그 이하 → `low`.

`review_status` 는 별개다. `machine_extracted` 는 사람이 눈으로 확인하지 않았다는 뜻이며,
현재 데이터는 전부 여기에 해당한다.

## 카테고리 분류

혜택 제목·설명에 대한 키워드 규칙으로 분류한다
(`scripts/collect-issuer-feed.mjs` 의 `CATEGORY_RULES`).

여러 업종이 섞인 문구는 **가장 먼저 언급된** 분야를 택한다.
예: "대형마트, 병원, 서점 등 5% 할인" → `shopping`.

어느 규칙에도 걸리지 않으면 `other` 다. 상세 섹션 제목을 혜택으로 승격한 카드는
제목이 짧아 `other` 비중이 높다. 이는 분류 실패를 숨기지 않고 그대로 드러낸 값이다.
